# 1.65.a update: MapHandler.CurrentCampfire NullReferenceException

Game updated 1.64.a -> 1.65.a. Checked LogOutput.log
(`/home/nikoj/.config/r2modmanPlus-local/PEAK/profiles/Default/BepInEx/LogOutput.log`)
from an in-game test session after the update.

## Finding

27 occurrences of a caught `NullReferenceException` thrown from the vanilla
game's `MapHandler.get_CurrentCampfire`, surfacing through our own code:

```
[Error  :Sense of Direction] PointPingerPatches.ReceivePointRpcPrefix failed, falling back to vanilla for this ping: System.NullReferenceException: Object reference not set to an instance of an object
  at MapHandler.get_CurrentCampfire ()
  at SenseOfDirection.ItemPings.ItemPingDetector.FindNear (...)
  at SenseOfDirection.ItemPings.ItemPingSpawner.SpawnFor (...)
  at SenseOfDirection.Pings.PointPingerPatches.SpawnPingNow (...)
  at SenseOfDirection.Pings.PointPingerPatches.ReceivePointRpcPrefixImpl (...)
  at SenseOfDirection.Pings.PointPingerPatches.ReceivePointRpcPrefix (...)
```

Not a crash - `ReceivePointRpcPrefix`'s outer try/catch catches it and falls
back to a vanilla ping (`return true`). But it means item-ping detection,
ripple, scaling, and audio boost are all silently skipped for every ping hit
during this state, repeatedly, throughout a run (not just at the Airport,
which `ItemPingDetector.cs:452`'s existing `MapHandler.ExistsAndInitialized`
guard was written for).

## Root cause

Decompiled the current `Assembly-CSharp.dll` (1.65.a) to check:

```csharp
public static bool ExistsAndInitialized
{
    get
    {
        if (Exists) return Singleton<MapHandler>.Instance.hasFinishedStartRoutine;
        return false;
    }
}

public static GameObject GetCampfireRoot(int segmentIndex)
{
    if (segmentIndex >= 0)
        return Singleton<MapHandler>.Instance.segments[segmentIndex].segmentCampfire;
    return null;
}

public static Campfire CurrentCampfire =>
    GetCampfireRoot(Singleton<MapHandler>.Instance.currentSegment).GetComponentInChildren<Campfire>();
```

`ExistsAndInitialized` only checks `hasFinishedStartRoutine` - it says
nothing about whether the *current* segment's `segmentCampfire` field is
actually populated. When it's null, `CurrentCampfire`'s
`GetCampfireRoot(...).GetComponentInChildren<Campfire>()` throws NRE on the
null `GetCampfireRoot` result.

Most likely trigger: **TerrainRandomiser** is installed in this profile and
restructures map segments; it may be leaving `segmentCampfire` unset for a
segment in the game's new 42-map layout (devs' modder notes: "Number of maps
in build changed from 21 -> 42"). Not confirmed whether this is a regression
from the map-count change specifically or a pre-existing TerrainRandomiser
interaction that only started showing up now - not investigated further.

path needs to be checked directly in-game (or with a working Unity log)

## Suggested fix (not applied yet)

Add a null-safe wrapper around `MapHandler.CurrentCampfire` access (treat
"segment has no campfire object yet" as "no campfire" instead of letting the
getter throw) and use it at both call sites:
- `ItemPingDetector.cs:454`
- `CampfireIndicatorController.cs:52`
